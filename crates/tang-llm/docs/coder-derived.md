# Coder-Next: every kernel derived (`TANG_CODER_DERIVED=all`)

Goal: the Qwen3-Coder-Next engine (`flash/coder.rs`) with no hand-written CUDA —
every kernel generated by `tang-compile` from a tensor-IR graph and a schedule,
`coder_kernels.rs` deletable. Behind `TANG_CODER_DERIVED=all` until reviewed.

## What blocks deleting `coder_kernels.rs`

1. **Activation layout.** The hand int8 activations are `[codes: XQ8_T × n][f32 d: t × n/32]`;
   the IR's `Q8x32` is `[codes][(d, d·Σc)]`. Derived producers cannot feed hand consumers (or the
   reverse) without a copy, so the swap has to happen a whole layer at a time (norm → GEMV/experts
   → combine), not kernel by kernel.
2. **`Format::Q6K`** in the IR, and `Format::Q8_0` on the int8-MMA (batch / wide) stage — this PR adds
   `Format::Q8_0` on the Gemv stage only.
3. **Runtime extents.** IR shapes are bound before lowering. Decode attention's key count and the
   KV write position change every token: needs key-count bucketing (as `derived_attn.rs` pads to
   4096) plus a scatter-at-runtime-index output view.
4. **GDN decode state** (conv ring buffer, in-place state update): needs in-place outputs.

## Status (2026-11-07)

Done: the runner (`flash/derived_ops.rs`), five ops checked against the hand kernels / a CPU
reference on an RTX 3090 (`examples/coder_derived_ops.rs`, numbers in `BENCHMARKS.md` §
"Coder-Next: per-op hand vs derived"), `Format::Q8_0` + `IntMma::pos_tile` in the IR.

Not done: `TANG_CODER_DERIVED=all` does not exist yet — nothing above is wired into `coder.rs`,
so there are no engine gates (wide-check KL, greedy, batch-check, prefix) and no H200 / vLLM
numbers. Order of the remaining work, by what unblocks the most:

1. Wire the MoE block whole (route → `coder_moe_ir`'s experts → `moe_combine_norm`) with the
   dense GEMVs as `gemv_q8_0` on GGUF bytes (load Q8_0 unrepacked under the switch). That swaps
   ~70% of decode time with no layout boundary inside a layer.
2. `gemv_q8_0` at T=8 is compute-bound (278 GB/s on a 3090 vs 862 at T=1): registers (8 positions ×
   32 code words), try `pos_tile` 4 × two passes, or the int8 MMA stage with Q8_0.
3. Decode attention: split-K with key-count buckets + a runtime-position KV scatter view.
4. GDN decode step: in-place state outputs (or double-buffered state) + the conv ring.
5. `Format::Q6K`, MTP head, embedding/copies.

## Constraints for wiring it in (from the prod rollout, 2026-11-07)

- An NVRTC/lowering failure falls back **per op** to the hand kernel, never disables a whole path
  (tang#180: a silent chunked-GDN failure turned off wide prefill, 45k TTFT went to 105 s in prod).
- Prod decodes with `serve --batch 45` + MTP: decode GEMVs run at T≈8–45, not T=1. Bench
  T=8/16/48 on an H200 before proposing anything for prod. The 3090 T=8 number (278 GB/s) is the one that matters.
- Startup already spends ~120 s building kernels: keep added compile time small, or cache the PTX
  under `/workspace/zest/kernels`.
- Behind a switch, off by default. Gates: flash-wide-check, batch-check N=8 bitwise, a continuation case.

## Part 2 (2026-11-07): `TANG_CODER_DERIVED=moe`

- `derived_ops::moe_block`: one decode window's MoE layer after the router, as one graph — top-k
  routing, gathered Q4_K/Q5_K gate and up GEMVs (x int8 per 32), SwiGLU int8, gathered Q5_K down,
  Q8_0 shared expert (dp4a at T=1, int8 tensor cores past that), combine, residual, next norm. Then
  `engine_q8` writes the next layer's int8 activations in the hand kernels' layout (codes as Q8x32,
  then f32 scales over the scale pairs; `mxq` got 1/8 more bytes for that).
  GPU check vs a plain-Rust reference (`examples/coder_derived_moe.rs`, 3090): max rel err 2.6e-7
  (T=1) to 5.6e-7 (T=16). 512 experts / top-10, µs a layer on the 3090: T=1 92, T=2 137, T=8 295,
  T=16 523. 13–16 kernels, ~0.4 s to build a shape.
- `coder.rs`: `enqueue_moe` runs it after the (still hand) router when `TANG_CODER_DERIVED` names
  `moe` or `all`, outside wide windows and `shared_par`. A shape that fails to build (Q6_K down: one
  layer; any lowering error) falls back to the hand kernels for that shape only and says so once.
  Narrow shapes (T=1..MAX_T × each layer's formats) are built at load, since nothing builds
  inside a graph capture; batch-window shapes are built on first use outside a capture, else
  they run on the hand kernels.
- Not run on the model yet: the 80B GGUF needs the H200. Gates to run there: flash-wide-check
  (3k/8k, int8 + bf16 KV), greedy equal, batch-check N=8, cached-prefix continuation, plus
  decode tok/s at T=1/8/16/48 against the hand engine.
